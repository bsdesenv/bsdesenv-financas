# Mobile UX for personal-finance dashboards

Scope: evidence-backed implications for the app’s current phone, tablet, and desktop patterns. Current app observations link to the existing source files; no application code was changed. Platform pages without a published version/date were checked on 22 November 2026.

## How should frequent financial tasks and quick entry be prioritized on phone?

### Takeaway

Keep transaction capture one of the shortest, always-available paths, while making the home screen useful for a quick financial check-in. Use defaults and shortcuts to remove repeat work, but validate the task ranking with this app’s own usage data rather than assuming every finance user has the same priorities. — [Apple HIG: Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data.md) · [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)

### Cited Findings

- Apple’s current HIG recommends gathering information in advance, prefilling reasonable defaults, offering choices instead of unnecessary text entry, supporting available input methods including paste, and validating numeric input as people enter it. Its “Entering data” page’s change log is dated 21 June 2023. — [Apple HIG: Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data.md)
- Progressive disclosure should keep frequently needed options visible and defer specialized choices; NN/g recommends using usage statistics and observational testing to decide what belongs in the initial view. This article is dated 4 December 2006. — [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- For forms, NN/g recommends removing unnecessary fields, putting labels close to fields (above them on mobile), using a single column, and ordering fields logically. This article is dated 1 May 2016. — [NN/g: Website Forms Usability](https://www.nngroup.com/articles/web-form-design/)
- In the current app, the persistent phone “Novo lançamento” action opens a mobile-specific amount keypad; the date defaults to today, categories are ordered by recent use, the description is optional, and “Salvar e novo” supports repeated entry. The free-form quick-entry field is desktop-only. — [App entry and quick-entry flow](../../src/App.html#L574-L599) · [New-transaction flow](../../src/App.html#L1254-L1430) · [Phone entry layout](../../src/Estilos.html#L530-L585)

### Inferences

- Keep the phone happy path to **amount → category → save**, with today preselected and description optional. The app already has these elements; the evidence supports defaults and minimizing required entry. Keep date changes, description suggestions, and other less frequent choices available without making them prerequisites. — [Apple HIG: Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data.md) · [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- Keep the custom keypad as a fast touch option, but offer an editable/paste-capable amount path as well. For editable web fields, `inputmode="decimal"` asks the browser for a fractional-numeric keyboard with the locale’s format separator; the HTML Standard defines this as a user-agent hint, not input validation. The standard was last updated 22 November 2026. — [WHATWG HTML Living Standard: `inputmode`](https://html.spec.whatwg.org/multipage/interaction.html#input-modalities:-the-inputmode-attribute) · [Apple HIG: Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data.md)
- Keep common/recent categories immediately visible and make the full category set an explicit, discoverable next step. The phone picker currently places all category chips in a horizontally scrolling strip; a clearly labeled “Todas as categorias” action or searchable vertical picker would reduce reliance on discovering off-screen chips. Treat this as a usability hypothesis to test, not a universal rule. — [Current category picker](../../src/App.html#L1309-L1324) · [Apple HIG: Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data.md)
- Preserve “Salvar e novo” as a secondary repeated-entry action and keep the primary save unmistakable. Continue to show the parsed/formatted amount and immediate validation feedback, particularly for Brazilian decimal and thousands separators. — [Current new-transaction flow](../../src/App.html#L1293-L1304) · [Apple HIG: Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data.md)

### Gaps

- The sources do not establish whether adding a transaction, planning a month, or reviewing the year is this app’s most frequent task. Use task analytics and short usability sessions to confirm the order and which shortcuts earn persistent space. — [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- Test the custom keypad and any alternate amount-entry path with screen readers, hardware keyboards, paste, and locale-specific input on the browsers/devices people actually use; Apple recommends supporting available input methods, while keyboard access is a WCAG requirement. — [Apple HIG: Entering data](https://developer.apple.com/design/human-interface-guidelines/entering-data.md) · [WCAG 2.2, SC 2.1.1 Keyboard](https://www.w3.org/TR/WCAG22/#keyboard)

## Which mobile navigation, touch-target, one-handed, and form practices are supported by current guidance?

### Takeaway

Use a small, labeled set of top-level destinations and visually distinguish the primary Add action from navigation. Treat platform target sizes as the practical design target and WCAG’s AA minimum as a conformance floor. Bottom placement is a useful convention, not a guarantee that every control is within every user’s thumb reach. — [Apple HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars.md) · [Material 3: Navigation bar](https://m3.material.io/components/navigation-bar/guidelines) · [WCAG 2.2, SC 2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum) · [NN/g: Bottom Sheets](https://www.nngroup.com/articles/bottom-sheet/)

### Cited Findings

- **WCAG requirement:** WCAG 2.2 Level AA Success Criterion 2.5.8 requires pointer targets to be at least 24 × 24 CSS pixels or meet its spacing/other exceptions. The 44 × 44 CSS-pixel “Target Size (Enhanced)” criterion is Level AAA, not AA. WCAG 2.2 became a W3C Recommendation on 12 December 2024. — [WCAG 2.2, SC 2.5.8](https://www.w3.org/TR/WCAG22/#target-size-minimum) · [WCAG 2.2, SC 2.5.5](https://www.w3.org/TR/WCAG22/#target-size-enhanced)
- **Platform recommendations:** Apple’s HIG gives 44 × 44 pt as a general button hit-region rule. Material 3 says to consider at least 48 × 48 dp for most touch targets and about 8 dp spacing. These are platform design recommendations, not the WCAG AA threshold. CSS px, pt, and dp are logical units and should not be treated as raw hardware pixels. — [Apple HIG: Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons.md) · [Material 3: Target sizes](https://m3.material.io/foundations/designing/structure) · [W3C: CSS pixel definition](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- Apple defines tab bars as navigation among top-level sections, not as a place for actions; it recommends labels, keeping the bar visible, and avoiding overflow. Its iPad guidance allows a tab bar to adapt to a sidebar. — [Apple HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars.md)
- Material 3 recommends a bottom navigation bar for three to five main destinations, with an icon and label per destination. It treats a FAB as a primary constructive action; compact layouts commonly place it near the lower trailing edge or above the navigation bar, and the FAB should not obstruct navigation. Material’s live guidance also allows a FAB to be nested in a navigation component. — [Material 3: Navigation bar](https://m3.material.io/components/navigation-bar/guidelines) · [Material 3: FAB](https://m3.material.io/components/floating-action-button/guidelines)
- Thumb reach varies with grip. NN/g cautions that a bottom sheet is not automatically easier to reach: people hold phones in different ways, and the bottom is not universally the easiest region; its bottom-sheet article is dated 11 June 2023. NN/g’s touch-target article (5 May 2019) summarizes a one-handed thumb study as supporting targets around 1 cm square for quick, accurate selection; that is usability evidence, not a WCAG or platform conformance requirement. — [NN/g: Bottom Sheets](https://www.nngroup.com/articles/bottom-sheet/) · [NN/g: Touch Targets on Touchscreens](https://www.nngroup.com/articles/touch-target-size/)
- For web forms, the HTML Standard says `inputmode="decimal"` should prompt a virtual keyboard capable of fractional numeric input and the locale’s separator. Android’s native guidance similarly says to declare an input type so the system can show an appropriate soft keyboard. — [WHATWG HTML Living Standard: `inputmode`](https://html.spec.whatwg.org/multipage/interaction.html#input-modalities:-the-inputmode-attribute) · [Android Developers: Specify the input method type](https://developer.android.com/develop/ui/views/touch-and-input/keyboard-input/style)

### Inferences

- The current phone bar has four destinations—Início, Extrato, Mês, Ajustes—and a visually distinct central Add action. Keep Add semantically an action, not a fifth destination; preserve visible labels on destinations and a clear accessible name for Add. The current add button has an accessible name, while the navigation items have labels. — [Current navigation markup](../../src/App.html#L565-L599) · [Current navigation sizing](../../src/Estilos.html#L133-L148) · [Material 3: Navigation bar](https://m3.material.io/components/navigation-bar/guidelines)
- Planilha is not a phone navigation item; it is reachable through “Ver o ano inteiro na planilha” from Mês. Keep that route explicit, and add another top-level destination only if usage evidence justifies the space and a destination can be traded/combined. — [Current month and spreadsheet routes](../../src/App.html#L1059-L1070) · [Apple HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars.md)
- The app’s CSS gives bottom navigation items a 52 px minimum height and the central Add control a 56 × 56 px box, and uses safe-area padding. Verify the *actual hit regions* at 320, 360, 390, and 430 CSS px, especially whether flex sizing or long localized labels reduce usable width. — [Current navigation sizing](../../src/Estilos.html#L133-L148)
- Keep the transaction sheet’s sticky save action and compact amount controls, but do not justify its bottom anchoring solely as a thumb-reach solution. Test one-handed reach across device sizes and both hands; on tablets, evaluate a wider layout or sidebar/rail transition. The current app keeps bottom navigation until 1024 px and then shows a sidebar, while Material and Apple describe adaptive navigation patterns for larger windows. — [Current breakpoints](../../src/Estilos.html#L648-L739) · [NN/g: Bottom Sheets](https://www.nngroup.com/articles/bottom-sheet/) · [Apple HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars.md)

### Gaps

- Neither platform guidance nor general thumb-zone research identifies one universally best position for this app’s Add control. Test one-handed use with varied hand sizes, grips, screen heights, and left/right hands; do not infer reach from a 390 px mockup alone. — [NN/g: Bottom Sheets](https://www.nngroup.com/articles/bottom-sheet/)
- The appropriate tablet transition depends on actual task density and usage. The app’s 640/1024 px breakpoints should be checked at intermediate widths and landscape orientation; design-system breakpoints are references, not mandatory values. — [Current breakpoints](../../src/Estilos.html#L648-L739) · [Material 3: Navigation bar](https://m3.material.io/components/navigation-bar/guidelines) · [Apple HIG: Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars.md)

## How can a dense financial dashboard and yearly spreadsheet adapt without hiding important information?

### Takeaway

At 320–430 CSS px, keep ordinary dashboard content in a single vertical reading flow, retain the key financial totals and the distinction between actual and planned values, and put only secondary detail behind explicit controls. Keep a 12-month grid when side-by-side comparison matters, but isolate horizontal scrolling to an accessible table region; offer a stacked/month-focused view as a companion for non-comparison tasks. — [WCAG 2.2, SC 1.4.10 Reflow](https://www.w3.org/TR/WCAG22/#reflow) · [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/) · [MOJ Design System: Scrollable pane](https://design-patterns.service.justice.gov.uk/components/scrollable-pane/)

### Cited Findings

- **WCAG requirement:** WCAG 2.2 SC 1.4.10 (Level AA) requires ordinary vertically read content to reflow at a width equivalent to 320 CSS px without loss of information/functionality or two-dimensional page scrolling. A data table may use two-dimensional layout when needed for its meaning, but the exception applies only to that table; surrounding headings, controls, and text still need to reflow. The Understanding page was updated 4 October 2026. — [WCAG 2.2 Recommendation, SC 1.4.10](https://www.w3.org/TR/WCAG22/#reflow) · [WAI Understanding Reflow (updated 4 October 2026)](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- NN/g’s mobile-table guidance recommends sticky headers and row labels for long grids, a clear cue when horizontal scrolling is available, and user control over which data is shown; it calls rotating the phone a last resort. The article is dated 17 September 2017. NN/g’s 2022 data-table guidance likewise recommends freezing header rows/columns and making hidden/reordered columns discoverable and accessible. — [NN/g: Mobile Tables](https://www.nngroup.com/articles/mobile-tables/) · [NN/g: Data Tables](https://www.nngroup.com/articles/data-tables/)
- W3C WAI recommends semantic table headers: use `<th scope="col">` and `<th scope="row">` for simple row/column relationships and a `<caption>` to identify the table. — [WAI: Tables with Two Headers](https://www.w3.org/WAI/tutorials/tables/two-headers/) · [WAI: Tables Tutorial](https://www.w3.org/WAI/tutorials/tables/)
- The UK Ministry of Justice Design System’s official scrollable-pane component (updated October 2026) is for content that unavoidably overflows. It uses a named, keyboard-focusable `role="region"` and edge shadows to signal horizontal overflow. — [MOJ Design System: Scrollable pane](https://design-patterns.service.justice.gov.uk/components/scrollable-pane/)
- Current app observations: the phone dashboard presents a financial hero, four KPI cards, category preview, recent transactions, and a year chart; category rows after the first four are hidden below 640 CSS px, with “Ver todas” leading to Mês. The year grid already has a sticky month header, sticky category column, current-month highlight/initial positioning, caption, and row/column scopes. Its scroll wrapper currently has `overflow: auto`, but no explicit `tabindex`, region role, accessible name, or visible overflow cue in the markup. — [Dashboard and category preview](../../src/App.html#L623-L628) · [Category and transaction cards](../../src/App.html#L913-L977) · [Year table markup](../../src/App.html#L1092-L1161) · [Responsive rules and table styling](../../src/Estilos.html#L462-L485) · [Phone category truncation](../../src/Estilos.html#L729-L739)

### Inferences

- Preserve the first-screen order around “available now,” its clear explanation, and the most useful month totals; keep actual, planned, and forecast amounts textually distinguishable. Use color as reinforcement, not the only status cue, and do not collapse a key number merely to shorten the page. The current hero and category notes already label “Já saiu,” “Planos sem lançamento,” and “Disponível”; the mobile category preview also has a “Ver todas” route. — [Current hero/KPI and category content](../../src/App.html#L650-L775) · [WCAG 2.2: Use of Color](https://www.w3.org/TR/WCAG22/#use-of-color)
- Treat the first four category rows, six recent transactions, and annual chart as mobile previews; make “Ver todas”/“Ver extrato” and the year details easy to find. If users need more dashboard detail, defer explanatory copy or secondary diagnostics before hiding important totals or transaction status. — [Current dashboard sections](../../src/App.html#L913-L977) · [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- For the yearly spreadsheet, **retain the scrollable grid for cross-month comparison**: keep the category column and month headers visible, preserve the current-month focus, add an edge fade/arrow or short instruction that signals horizontal scrolling, and make the wrapper focusable, named, and keyboard-scrollable. Current markup already supplies the table caption and semantic header scopes; the scroll region is the notable opportunity. — [Current year table](../../src/App.html#L1092-L1161) · [MOJ Design System: Scrollable pane](https://design-patterns.service.justice.gov.uk/components/scrollable-pane/) · [WAI: Tables with Two Headers](https://www.w3.org/WAI/tutorials/tables/two-headers/)
- Add a complementary phone overview for people who want to inspect one month or category rather than compare all twelve months: e.g. a month selector plus vertically stacked month/category summaries, with a clear “Grid view” route. Do not make stacked cards the only presentation if users need to compare months directly; preserve CSV/export for spreadsheet-oriented work. — [NN/g: Mobile Tables](https://www.nngroup.com/articles/mobile-tables/) · [Current CSV export and month navigation](../../src/App.html#L1092-L1153)
- Keep table scrolling contained to its own region so the rest of the page reflows at narrow widths and zoom. On tablets, allow more columns to show naturally; keep a deliberate full-grid option on desktop rather than forcing phone users to rotate their device. — [WAI Understanding Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) · [NN/g: Mobile Tables](https://www.nngroup.com/articles/mobile-tables/)

### Gaps

- Which dashboard numbers are decision-critical, which categories deserve the initial preview, and whether users primarily compare months or inspect one month cannot be determined from general guidelines or code alone. Validate with task-based testing and, where appropriate, feature-use data. — [NN/g: Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- Check 320 px reflow, 200% text enlargement/zoom, horizontal table navigation by touch and keyboard, screen-reader table context, and the 640–1024 px tablet transition on real browsers. WCAG’s table exception permits necessary two-dimensional layout; it does not establish that a particular scroll treatment is understandable or convenient.
